# Tsunagi — API_SPEC.md

REST + WebSocket API for the Tsunagi backend (FastAPI). All endpoints are
versioned under `/api/v1`. The OpenAPI document is auto-generated by FastAPI
and served at `/docs` (Swagger UI) and `/openapi.json`.

Related docs: [ARCHITECTURE.md](ARCHITECTURE.md) ·
[DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) · [ROADMAP.md](ROADMAP.md)

---

## Conventions

- **Base URL:** `https://<your-server>/api/v1`
- **Liveness:** `GET /health` → `{"status": "ok", "version": "0.1.0"}` (no auth).
- **Format:** JSON request/response bodies, UTF-8.
- **Timestamps:** ISO 8601 with timezone, e.g. `2026-08-12T09:30:00Z`.
- **IDs:** UUIDv4 strings. Message IDs are generated by the **client** so
  uploads are idempotent.

### Authentication

Every endpoint (except device registration with a setup key) requires:

```http
Authorization: Bearer <token>
```

Three credential types share the same header:

| Credential      | Issued by                     | Scope                                  |
|-----------------|-------------------------------|----------------------------------------|
| Device token    | `POST /devices/register`      | Upload messages, report presence and capture health (device scope) |
| API key         | Dashboard / API keys API      | Read messages (`user`), manage devices and keys (`admin`) |
| Enrolment code  | `POST /enrolments` (admin)    | One device registration, then spent    |
| Setup key       | `TSUNAGI_SETUP_KEY` config    | Device registration; legacy, off by default |

### What each scope reaches

| Endpoint group | `device` | `user` | `admin` |
|---|:--:|:--:|:--:|
| `POST /messages`, `/messages/batch` | ✅ | — | — |
| `GET /messages`, `/search`, `/wait` | — | ✅ | ✅ |
| `GET /devices`, `/stats`, `/stats/volume` | — | ✅ | ✅ |
| `POST /devices/{id}/enabled`, `DELETE /devices/{id}` | — | — | ✅ |
| `DELETE /devices/{id}/messages` | — | — | ✅ |
| `/keys` (all methods) | — | — | ✅ |
| `/enrolments` (all methods) | — | — | ✅ |
| `GET /events` | — | — | ✅ |
| `GET /me` | ✅ | ✅ | ✅ |
| `/ws/messages` | — | ✅ | ✅ |

Events are admin-only because they name devices and API keys and record failed
authentication attempts.

Device tokens are prefixed `tsn_dev_` and API keys `tsn_key_`; the server uses
the prefix to decide which store to check. Only a SHA-256 digest is persisted,
so raw values are recoverable only at the moment they are issued.

On a fresh install with no keys, the server mints one admin key at startup and
logs it once. Set `TSUNAGI_BOOTSTRAP_API_KEY` to pin that value instead.

### Errors

Errors use a consistent envelope:

```json
{
  "error": {
    "code": "unauthorized",
    "message": "Invalid or expired token."
  }
}
```

| Status | Code               | Meaning                                  |
|--------|--------------------|------------------------------------------|
| 400    | `bad_request`      | Malformed body or query parameters       |
| 401    | `unauthorized`     | Missing/invalid token                    |
| 403    | `forbidden`        | Token valid but lacks required scope     |
| 404    | `not_found`        | Resource does not exist                  |
| 409    | `conflict`         | Duplicate resource (non-idempotent path) |
| 422    | `validation_error` | Field-level validation failure (FastAPI) |
| 429    | `rate_limited`     | Too many requests                        |

### Rate limiting

Requests are counted in a fixed window per credential, or per client address
when unauthenticated — so a failed login attempt still consumes budget, which is
what makes credential guessing expensive. Defaults are 240 requests per 60
seconds, configurable via `TSUNAGI_RATE_LIMIT_REQUESTS` and
`TSUNAGI_RATE_LIMIT_WINDOW_SECONDS`.

Every response carries the remaining budget:

```http
X-RateLimit-Limit: 240
X-RateLimit-Remaining: 237
```

A rejected request returns `429` with `Retry-After` in seconds. `GET /health`
is exempt so probes cannot be throttled, and WebSocket connections are not
counted — a long-lived socket is one request, and limiting it would only
penalise reconnects.

The Android app is unaffected in normal use: it batches uploads, so a backlog of
hundreds of messages is a handful of requests.

## Enrolment

Single-use codes that authorize exactly one device registration. They replace
the shared setup key: a leaked code is worth one device for a few minutes rather
than unlimited devices forever, and every enrolment is attributable to the admin
who issued it.

### Issue a Code

```http
POST /api/v1/enrolments
```

Admin scope.

```json
{ "label": "Arun's Pixel", "ttl_seconds": 900 }
```

Both fields are optional; `ttl_seconds` defaults to
`TSUNAGI_ENROLMENT_TOKEN_TTL_SECONDS` (900) and accepts 60–86400.

Response `201 Created`:

```json
{
  "id": "…", "code": "KRHK-4JEN", "label": "Arun's Pixel", "status": "pending",
  "created_at": "…", "expires_at": "…",
  "used_at": null, "cancelled_at": null, "used_by_device_id": null
}
```

`code` appears **only here**; only its hash is stored. It is eight characters
from an alphabet with `I`, `L`, `O`, `U`, `0`, and `1` removed, since it gets
typed by hand off a screen. Redemption accepts any capitalisation and ignores
dashes and spaces, so `krhk4jen` works.

### List and Cancel

```http
GET    /api/v1/enrolments        # 200 { enrolments: [...] }  (never includes `code`)
DELETE /api/v1/enrolments/{id}   # 204, or 409 if already used
```

`status` is `pending`, `used`, `expired`, or `cancelled`. A used code records
`used_by_device_id`, which is the audit trail from code to device.

### Redeeming

Present the code as the bearer token on `POST /devices/register`. It is consumed
in the same transaction as the device row, so a failed registration does not
burn the code and two phones racing on one code cannot both win.

Rejections are `403` with a code naming the reason: `enrolment_used`,
`enrolment_expired`, or `enrolment_cancelled`. A well-formed code that was never
issued is `401`.

## Identity

### Describe the calling credential

```http
GET /api/v1/me
```

Any authenticated credential. Lets a client discover what it may do instead of
probing endpoints and collecting 403s — the dashboard uses it to hide actions a
`user` key cannot perform.

```json
{ "kind": "key", "scope": "admin", "name": "bootstrap-admin", "id": "…" }
```

`kind` is `key`, `device`, or `setup`; `scope` is `device`, `user`, or `admin`.

## Devices

### Register Device

```http
POST /api/v1/devices/register
```

Registers an Android device and issues its device token. The token is shown
**once**; the device stores it locally.

Authenticated with a single-use enrolment code, an admin API key, or the legacy
setup key when one is configured.

Request:

```json
{
  "device_name": "Office Phone"
}
```

Response `201 Created`:

```json
{
  "device_id": "6f1c1c9e-3f7a-4b62-9e2d-8f0a1b2c3d4e",
  "token": "tsn_dev_9f8e7d6c5b4a..."
}
```

### List Devices

```http
GET /api/v1/devices
```

Requires user/admin scope. Response `200 OK`:

```json
{
  "devices": [
    {
      "id": "6f1c1c9e-...",
      "name": "Office Phone",
      "status": true,
      "enabled": true,
      "last_seen": "2026-08-12T09:28:41Z",
      "created_at": "2026-08-01T14:02:11Z",
      "disabled_at": null,
      "capture": "ok",
      "capture_reported_at": "2026-08-12T09:28:41Z",
      "capture_permitted": true,
      "inbox_readable": true,
      "battery_exempt": true,
      "last_captured_at": "2026-08-12T09:11:03Z",
      "last_swept_at": "2026-08-12T09:28:41Z"
    }
  ]
}
```

`status` is `true` when the device has been seen within the online window
(`TSUNAGI_DEVICE_ONLINE_WINDOW_SECONDS`, default 1800) **and** is enabled.

The phone refreshes `last_seen` on every authenticated call, including a
check-in it makes when it has nothing to upload. Without that check-in a quiet
device would be indistinguishable from a dead one; the window is wider than the
15-minute floor Android imposes on background work, so one missed beat does not
flip a healthy device to offline. `enabled` is `false` when an admin has
switched it off. Revoked devices are omitted entirely.

`capture` answers a different question from `status`, and the two can disagree:

| Value | Meaning |
|---|---|
| `ok` | The phone reports it can still receive SMS. |
| `blocked` | SMS permission was revoked, or the phone cannot read its SMS store. Nothing is being captured. |
| `unknown` | The device has never reported — an app older than this field, not a device in trouble. |

`status` cannot stand in for it. A phone answers the check-in as long as the app
can run at all, which it does perfectly well after its SMS permission has been
revoked: online, uploading nothing, capturing nothing. Where `capture` is `ok`,
`last_captured_at` is what separates a phone that is merely quiet from one worth
investigating.

### Report Capture Health

```http
POST /api/v1/devices/checkin
```

Device scope. Sent by the phone on every sync pass, with or without messages.
Presence is refreshed by any authenticated call; this carries what the server
cannot work out for itself.

```json
{
  "capture_permitted": true,
  "inbox_readable": true,
  "battery_exempt": false,
  "last_captured_at": "2026-08-12T09:11:03Z",
  "last_swept_at": "2026-08-12T09:28:41Z"
}
```

`capture_permitted` is `RECEIVE_SMS` and `READ_SMS` still being granted;
`inbox_readable` is whether the last inbox sweep could read the platform SMS
store, which is a different fact from whether it found anything;
`battery_exempt` is exemption from battery optimization, which does not block
capture but allows the system to park the app where no broadcast is delivered.
The two timestamps may be `null` on a phone that has captured nothing yet.

Responds `200 OK` with the same device object `GET /devices` returns. A
transition into or out of `blocked` raises a `DEVICE_CAPTURE_BLOCKED` or
`DEVICE_CAPTURE_RESTORED` event; an unchanged report raises nothing, since a
blocked phone reports every fifteen minutes and one event per pass would bury
the transition.

### Turn a Device On or Off

```http
POST /api/v1/devices/{device_id}/enabled
```

Admin scope. Reversible suspension, as opposed to `DELETE`, which is permanent.

```json
{ "enabled": false }
```

Returns the updated `DeviceOut`. A suspended device's uploads are refused with
`403` and code `device_disabled`; re-enabling restores it immediately without
the phone needing to re-enrol.

> **Why 403 rather than 401.** The Android client treats `401` as "my token is
> stale" and re-enrols using its stored setup key. Answering `401` for a
> switched-off device would let it walk straight back in under a new id and
> defeat the off switch. `403` is terminal on the client.

### Clear a Device's Messages

```http
DELETE /api/v1/devices/{device_id}/messages
```

Admin scope. **Permanently deletes** every message uploaded by this device.
Not reversible, and there is no soft-delete or restore behind it. The device
itself is untouched — it stays registered, keeps its token, and goes on
uploading.

Response `200 OK` with the number of rows deleted, which is the only
confirmation available once the call has run:

```json
{ "deleted": 1284 }
```

Clearing a device that has no messages reports `0`. `404` if the device does
not exist.

Unlike the other device endpoints, a **revoked device is accepted** — clearing
a retired phone's messages is the ordinary reason to call this.

Recorded in the durable audit trail as `DEVICE_MESSAGES_CLEARED`, with the
device id, its name and the count. That entry is the only record that the
messages ever existed once the rows are gone.

> **Cleared is not erased.** This empties the table, not the deployment. Any
> database dump taken beforehand still contains these messages, including the
> one `deployment/update.sh` writes before every migration. If the requirement
> is that the data no longer exist anywhere, clearing is a first step and the
> backups are the rest of the job.

> **The phone is not touched.** Nothing is deleted from the device's own
> storage or from the Android SMS inbox, and the phone's local record of what
> it has already synchronized is unaffected — so cleared messages are not
> re-uploaded on the next sync. They can come back if that local record is
> reset, by a reinstall for instance, since the server no longer holds an id to
> recognise them by.

### Revoke Device

```http
DELETE /api/v1/devices/{device_id}
```

Requires admin scope. **Permanent** — use `POST /devices/{id}/enabled` to pause
a device instead. Messages already synchronized are retained. Response
`204 No Content`, or `404` if the device does not exist or is already revoked.

A revoked device's uploads are refused with `403` and code `device_revoked`.

## Messages

### Upload Message

```http
POST /api/v1/messages
```

Device scope. **Idempotent** — the client-generated `id` deduplicates retries:
re-uploading an existing `id` returns `200` with the stored record instead of
creating a duplicate.

Request:

```json
{
  "id": "b3d0aef2-91a4-4a8f-8f2e-77f0c9e1a5b6",
  "sender": "+15551234567",
  "body": "Your verification code is 482913",
  "received_at": "2026-08-12T09:27:03Z"
}
```

Response `201 Created` (or `200 OK` if it already existed):

```json
{
  "id": "b3d0aef2-...",
  "device_id": "6f1c1c9e-...",
  "sender": "+15551234567",
  "body": "Your verification code is 482913",
  "received_at": "2026-08-12T09:27:03Z",
  "created_at": "2026-08-12T09:27:09Z"
}
```

### Upload a Batch

```http
POST /api/v1/messages/batch
```

Device scope. Same per-item semantics as a single upload; up to 500 messages
per request. This is what the Android sync engine uses.

Request:

```json
{ "messages": [ { "id": "...", "sender": "...", "body": "...", "received_at": "..." } ] }
```

Response `200 OK`:

```json
{ "accepted": 3, "created": 2, "duplicates": 1, "rejected": 0, "results": null }
```

A replayed batch returns `created: 0`, which is the normal outcome when a
previous response was lost in transit.

By default one unacceptable message rejects the whole request with `422`, and
the message names which: `messages.1.sender: String should have at least 1
character`. Nothing in that batch is stored.

#### Per-message results

Add `"partial": true` to the request to have acceptable messages stored and the
rest reported instead:

```json
{
  "accepted": 3,
  "created": 2,
  "duplicates": 0,
  "rejected": 1,
  "results": [
    { "index": 0, "id": "6f1c...", "status": "created" },
    { "index": 1, "id": "8a2d...", "status": "rejected",
      "error": "messages.1.sender: String should have at least 1 character" },
    { "index": 2, "id": "9b3e...", "status": "created" }
  ]
}
```

`results` carries one entry per message in request order; `status` is `created`,
`duplicate` or `rejected`. `id` is absent only when the id itself was the
unreadable field, in which case `index` is the only handle on the message.

**Setting `partial` is a promise to read `results`.** It is off by default
because a client that ignores them would read `200` as "all stored" and drop the
one message the server refused — so an older client keeps the all-or-nothing
behaviour it already knows how to survive. A `null` `results` means every
message was stored or already present, which is what a `200` meant before this
field existed.

The batch size cap and the "at least one message" rule still apply to a partial
request, and still answer `422`: those describe the request, not a message in it.

### Export Messages

```http
GET /api/v1/messages/export
```

Requires user/admin scope. Takes the same filters as `GET /messages` — `sender`,
`device_id`, `after`, `before`, `query` — and no `limit`: an export that
silently stopped at a page boundary would be worse than no export.

| Parameter | Values | Default |
|---|---|---|
| `format` | `csv`, `json` | `csv` |

Messages come back **oldest first**, the opposite of the list endpoint: a file is
read from the top, and a backup that starts at the newest message reads
backwards. The response is streamed and carries
`Content-Disposition: attachment` with a timestamped filename.

```
id,device_id,sender,body,received_at,created_at
6f1c1c9e-...,8a2d...,+15550001111,"a body, quoted",2026-08-12T09:11:03+00:00,...
```

`format=json` returns `{"messages": [...]}` with the same objects `GET /messages`
returns. There is no `total`: counting first would mean a second full scan to
tell the caller something it learns by reading to the end.

A large export is a large response — the server streams it a chunk at a time
rather than building it in memory, but a client that buffers the whole body
should expect to hold it.

### List Messages

```http
GET /api/v1/messages
```

User scope. Query parameters:

| Parameter   | Type    | Default | Description                          |
|-------------|---------|---------|--------------------------------------|
| `limit`     | int     | 50      | Page size (max 200)                  |
| `offset`    | int     | 0       | Pagination offset                    |
| `sender`    | string  | —       | Exact sender filter                  |
| `device_id` | uuid    | —       | Restrict to one device               |
| `after`     | ISO8601 | —       | `received_at > after`                |
| `before`    | ISO8601 | —       | `received_at < before`               |

Response `200 OK`:

```json
{
  "total": 1342,
  "limit": 50,
  "offset": 0,
  "messages": [ { "id": "...", "sender": "...", "body": "...",
                  "received_at": "...", "device_id": "...", "created_at": "..." } ]
}
```

Ordered by `received_at` descending.

### Search Messages

```http
GET /api/v1/messages/search
```

User scope. Full-text search over message bodies.

| Parameter | Type   | Description                     |
|-----------|--------|---------------------------------|
| `query`   | string | Search terms (required)         |
| `sender`  | string | Optional sender filter          |
| `limit`   | int    | Page size (default 50, max 200) |
| `offset`  | int    | Pagination offset               |

Response shape matches List Messages.

### Wait For New Messages (long polling)

```http
GET /api/v1/messages/wait
```

User scope. Blocks until a new message arrives or the timeout elapses.

| Parameter | Type    | Default | Description                                    |
|-----------|---------|---------|------------------------------------------------|
| `since`   | ISO8601 | now     | Return messages stored after this instant      |
| `timeout` | int     | 30      | Max seconds to hold the request (max 60)       |
| `sender`  | string  | —       | Optional sender filter                         |

`since` compares against `created_at` (server storage time), not `received_at`.
Storage time is monotonic for a poller, whereas a device uploading a backlog
after being offline produces `received_at` values that move backwards.

Response `200 OK` with `messages: []` on timeout, or the new messages as soon
as they arrive. Intended for OTP-forwarding and scripting use cases where a
WebSocket is inconvenient.

## API Keys

Admin scope. Keys are returned in full **once** at creation.

```http
POST   /api/v1/keys      # { "name": "home-automation", "scope": "user" }
                         #   → 201 { id, name, scope, created_at, revoked_at, key }
GET    /api/v1/keys      # 200 { keys: [ { id, name, scope, created_at, revoked_at } ] }
DELETE /api/v1/keys/{id} # 204 — revokes immediately
```

`scope` is `user` (read messages, devices, events, stats) or `admin` (also
manage devices and keys); it defaults to `user`. Revocation is a soft delete:
the key stops authenticating immediately but remains listed with `revoked_at`
set, so past usage stays auditable.

## Events

System event log backing the dashboard's Events page. Events are transient
(capped ring buffer in Redis, last 1000) — this is observability data, not the
message record.

```http
GET /api/v1/events
```

User scope. Query parameters:

| Parameter | Type   | Default | Description                                        |
|-----------|--------|---------|----------------------------------------------------|
| `limit`   | int    | 100     | Max events to return (max 1000)                    |
| `level`   | string | —       | Filter: `info`, `warn`, `error`                    |
| `type`    | string | —       | Filter by event type (e.g. `MSG_RECV`)             |

Response `200 OK`:

```json
{
  "events": [
    { "timestamp": "2026-08-12T14:32:05.119Z", "type": "MSG_RECV",  "level": "info",
      "payload": { "id": "evt_9x8", "device_id": "...", "status": "delivered", "len": 42 } },
    { "timestamp": "2026-08-12T14:35:44.201Z", "type": "AUTH_FAIL", "level": "error",
      "payload": { "reason": "invalid api key format", "ip": "192.168.1.105" } }
  ]
}
```

Event types include `SYSTEM_INIT`, `MSG_RECV`, `SYNC_OK`, `SYNC_FAIL`,
`AUTH_FAIL`, `LATENCY_WARN`. Live tailing uses the WebSocket (`sync.event`
and `system.event` frames) — this endpoint provides the initial backlog.

## Audit Trail

```http
GET /api/v1/audit
```

Requires admin scope. The durable counterpart to `GET /events`: where that
serves the capped in-memory log the dashboard streams, this reads an append-only
table that survives a restart, is not capped, and paginates.

| Parameter | Meaning | Default |
|---|---|---|
| `limit` | 1–500 | 100 |
| `offset` | skip N | 0 |
| `level` | `info` / `warn` / `error` | — |
| `type` | exact event type, e.g. `DEVICE_REVOKED` | — |
| `after`, `before` | ISO-8601 bounds on `created_at` | — |

```json
{
  "total": 42,
  "limit": 100,
  "offset": 0,
  "events": [
    {
      "id": "9b3e...",
      "type": "DEVICE_CAPTURE_BLOCKED",
      "level": "error",
      "payload": { "device_id": "6f1c...", "reason": "SMS permission has been revoked on the device." },
      "created_at": "2026-08-31T10:44:22Z"
    }
  ]
}
```

Events are newest first. Message and sync traffic (`MSG_RECV`, `SYNC_OK`) is
**not** in the trail — the messages table already records it, and it would bury
the administrative and security events this exists for.

## WebSocket

```text
GET /ws/messages
Authorization: Bearer <api-key>   (or ?token=<api-key> for browser clients)
```

Server → client events (JSON frames, `type` discriminated):

```json
{ "type": "message.new",    "data": { "id": "...", "sender": "...", "body": "...", "received_at": "...", "device_id": "..." } }
{ "type": "device.status",  "data": { "device_id": "...", "status": true, "last_seen": "..." } }
{ "type": "sync.event",     "data": { "device_id": "...", "uploaded": 12 } }
{ "type": "system.event",   "data": { "type": "AUTH_FAIL", "level": "error", "payload": { } } }
```

Client → server:

```json
{ "type": "ping" }            → { "type": "pong" }
```

Delivery is best-effort (backed by Redis pub/sub); clients that need a gapless
record should reconcile with `GET /api/v1/messages?after=<last_seen_at>` after
reconnecting. PostgreSQL is always the source of truth.

## Webhooks

An endpoint this server calls when something happens, for integrations with no
browser to hold a WebSocket open and no reason to poll. Admin scope throughout.

### Register

```http
POST /api/v1/webhooks
```

```json
{
  "url": "https://example.com/tsunagi",
  "description": "ticketing system",
  "events": ["message.new"]
}
```

`events` defaults to `["message.new"]`; the full set is `message.new` and
`device.status`. Only the URL scheme is validated — which hosts are reachable is
the operator's business on a server they run themselves, and refusing loopback
would break the most common integration there is, a script on the same box.

Responds `201` with the webhook **and its signing secret**, which is shown once
and never again. Unlike an API key the secret is stored as issued rather than
hashed: it is not a credential presented to us but one we sign with, so the
server has to keep it.

### Deliveries

Each delivery is a `POST` with this body:

```json
{
  "event": "message.new",
  "delivered_at": "2026-08-29T15:12:31+00:00",
  "data": { "id": "6f1c...", "sender": "+15550001111", "body": "…" }
}
```

`data` is the same object the WebSocket carries for that event.

| Header | Meaning |
|---|---|
| `X-Tsunagi-Event` | The event name |
| `X-Tsunagi-Delivery` | Unique id for this attempt |
| `X-Tsunagi-Timestamp` | Unix seconds, covered by the signature |
| `X-Tsunagi-Signature` | `sha256=` + HMAC-SHA256 of `timestamp.body` |

Verify it before trusting the body:

```python
import hashlib, hmac

expected = "sha256=" + hmac.new(
    secret.encode(), f"{timestamp}.".encode() + raw_body, hashlib.sha256
).hexdigest()
if not hmac.compare_digest(expected, signature_header):
    raise ValueError("not from Tsunagi")
```

The timestamp is inside the signature so a captured delivery cannot be replayed
forever; reject one that is too old for you.

**Delivery is best-effort.** A delivery is retried up to three times when the
endpoint cannot be reached or answers `5xx`/`429`, and not at all on any other
`4xx` — that is the receiver saying it understood and refused. Twenty
consecutive failures switch the webhook off, so a dead endpoint stops costing
every message a timeout; turning it back on resets the count. The database
remains the record of what arrived: a webhook that missed something is not a
message that was lost.

### Manage

```http
GET    /api/v1/webhooks                  # list, without secrets
POST   /api/v1/webhooks/{id}/enabled     # {"enabled": false}
POST   /api/v1/webhooks/{id}/test        # send one now, inline
DELETE /api/v1/webhooks/{id}
```

`test` sends a signed `webhook.test` delivery immediately and answers with what
happened — `{"delivered": true, "status": 200, "error": null}` — rather than
queueing it, because the operator asking is asking about right now. A failed
test never switches the webhook off.
